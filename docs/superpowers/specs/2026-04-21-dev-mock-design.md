# 本地开发环境全量 Mock 设计

## 目标

在本地开发环境中，让前端现有接口请求全部走本地 mock 数据，不依赖真实后端服务。

本次改动限定如下：

- 仅影响本地开发环境
- 生产构建与生产接口行为保持不变
- 保持现有 `src/api/*.js` 的调用方式不变
- 覆盖当前项目中已经存在并被页面使用的接口

## 当前现状

项目当前已经有一套非常轻量的 mock 雏形：

- `src/main.js` 会直接执行 `src/server/mock/test.js`
- `src/server/mock/test.js` 当前只拦截了 `/mock/news`
- 业务接口仍然主要通过 `axios` 请求 `/api/**`
- `vite.config.js` 中开发服务器仍然配置了 `/api/` 代理到 `http://localhost:3000`

因此现在的 mock 只覆盖了演示接口，无法满足“开发环境所有接口都走 mock”的需求。

## 方案选择

### 方案 A：继续扩展浏览器端 `mockjs` 拦截

优点：

- 与现有 `src/server/mock/test.js` 最接近
- 初始改动量较小

缺点：

- 入口分散，后续接口多了会难维护
- 更适合演示级接口，不适合作为统一开发 mock 方案
- 容易与业务启动逻辑耦合

### 方案 B：使用 `vite-plugin-mock` 承担开发环境 mock

优点：

- 更符合 Vite 本地开发环境职责
- 只在开发环境生效，生产更安全
- mock 文件可以按业务拆分，便于扩展
- 业务层 `axios` 和 `src/api/*.js` 无需大改

缺点：

- 需要补一层目录结构和 Vite 配置

### 方案 C：在 `src/utils/http.js` 中手动分发本地假数据

优点：

- 无需新增插件

缺点：

- 请求层和 mock 数据强耦合
- 后续维护成本高
- 不适合继续扩展

## 最终方案

采用方案 B：使用 `vite-plugin-mock` 在本地开发环境中接管 `/api/**` 请求。

## 设计细节

### 1. 接入方式

- 在 `vite.config.js` 中接入 `vite-plugin-mock`
- 仅开发环境启用 mock
- 保留现有 `/api/` 前缀，mock 直接匹配当前接口路径
- 生产构建不启用该插件

### 2. 目录结构

新增根目录 `mock/`，按业务模块拆分 mock 定义：

- `mock/system.js`
- `mock/user.js`
- `mock/index.js`（如果需要集中导出）

旧的 `src/server/mock/test.js` 不再作为主入口：

- 从 `src/main.js` 移除其执行逻辑
- 避免浏览器端 mock 和 Vite mock 两套机制并存

### 3. 接口覆盖范围

本次优先覆盖项目中已经明确存在的接口：

- `POST /api/base/login`
- `POST /api/api/system/addmenu`
- `GET /api/api/system/menu`
- `POST /api/api/system/deletemenu`
- `GET /api/api/user/list`
- `GET /api/api/system/roles`
- `GET /api/api/system/userroles`

如果在实现阶段发现还有页面实际访问但未收录的接口，则补齐到 mock 中。

### 4. 数据结构原则

mock 返回值必须与当前页面消费方式兼容，不额外发明新协议。

约束如下：

- 登录接口返回 `success`、`token`，满足当前登录流程
- 列表接口返回页面现有代码能直接渲染的字段
- 增删改接口返回成功标记和必要消息
- 对于菜单、用户、角色等模块，字段命名保持与现有页面一致

### 5. 状态管理策略

为了让本地开发操作更接近真实场景：

- 菜单增删接口会在 mock 进程内维护一份可变数据
- 列表接口读取同一份内存数据
- 页面刷新后数据允许恢复为初始 mock 状态

这样既能支持前端联调，也不会引入额外存储复杂度。

### 6. 请求流转

开发环境下：

1. 页面调用 `src/api/*.js`
2. `axios` 发起 `/api/**` 请求
3. Vite 开发服务器上的 mock 插件拦截请求
4. 返回本地 mock 数据给页面

生产环境下：

1. 页面调用 `src/api/*.js`
2. `axios` 仍按原有生产配置请求真实后端

## 错误处理

- 登录失败时返回与当前提示逻辑兼容的错误消息
- 不存在的数据删除请求返回失败结果
- 非法参数尽量返回结构化错误信息，避免页面直接崩溃

## 验证方式

实现完成后至少验证以下内容：

- 本地开发环境启动时不再依赖 `localhost:3000`
- 登录页可以通过 mock 接口成功登录
- 菜单列表接口可正常展示
- 菜单新增、删除操作不会报错
- 用户列表、角色列表、用户角色查询接口可正常返回数据
- 生产构建可以继续成功执行

## 非目标

本次不包含以下内容：

- 不做生产环境 mock
- 不做真实接口与 mock 的运行时切换 UI
- 不补不存在页面的扩展接口
- 不引入持久化存储保存 mock 改动

## 风险与控制

### 风险 1：mock 返回字段与页面期望不一致

控制方式：

- 以现有页面实际消费字段为准设计 mock 数据
- 在实现前先检查对应页面字段依赖

### 风险 2：两套 mock 机制同时生效导致行为冲突

控制方式：

- 明确移除 `src/main.js` 中旧 mock 入口调用
- 统一由 Vite mock 负责开发环境拦截

### 风险 3：生产环境误带 mock 逻辑

控制方式：

- 仅在开发环境启用插件
- 构建后再次验证生产打包结果
